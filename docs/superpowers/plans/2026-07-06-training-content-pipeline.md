# Training Content Pipeline — Program Plan

> **For agentic workers:** This is a PROGRAM plan — phases scoped for sequencing and design. Before executing a phase, write a dated task-level implementation plan for it via `superpowers:writing-plans` (bite-sized TDD tasks), referencing this doc as the spec. Do not implement directly from this document.

**Goal:** Repeatable, auto-updating training materials for every operational role (coach, referee, venue manager, front-of-house, director, event lead, …): per-role slide decks generated from the ops catalog, and screen-capture walkthrough videos of the core product workflows regenerated by one command — so training content can never silently drift from the product.

**Architecture:** Two generators sharing the repo's content-as-code idiom. (1) Decks extend the existing ops-catalog render pipeline (`scripts/ops-catalog/index.ts` → views in `src/lib/ops-catalog/views/`), so the CI artifacts-up-to-date check keeps them current exactly like role manuals. (2) Videos are Playwright *walkthrough scripts* — a separate Playwright project with `video: 'on'` driving staging-seeded accounts — regenerated on demand, never committed (large binaries; output is gitignored).

**Tech Stack:** Existing only — TypeScript, the ops-catalog loader/views, Playwright (already a dev dependency), plain self-contained HTML/CSS/JS for decks. No new services; TTS narration is an explicitly optional Phase 3 add-on behind an env key.

## Global Constraints

- Decks must be **self-contained HTML** (inline CSS/JS, no CDN) so they open from disk and print to PDF; one file per role under `docs/operations/artifacts/training/`.
- Generated decks follow the manuals' contract: byte-stable output for unchanged catalog input (the ops-catalog CI check diffs rendered artifacts). Respect `manual_target: hand_authored` semantics where applicable — hand-authored *content* is composed by reference, never overwritten.
- Walkthrough videos and screenshots are **build artifacts, not repo content**: output under `training/output/` (gitignored). Scripts, captions, and narration text ARE repo content.
- Walkthrough specs are NOT tests: separate Playwright project/config so `npm test` and CI never run them; they run only via `npm run training:videos` against a locally running dev server (staging DB, seeded accounts).
- Walkthroughs must follow the repo's Playwright conventions (`waitForHydration`, element clicks over keydown, `domcontentloaded` when R2_MOCK images are present).
- Walkthroughs must be **read-mostly**: where a flow requires writes (submit application, record assessment), use dedicated `training+<role>@test.aspiresports.com` fixture data and clean up or make the write idempotent — never mutate the shared seeded accounts' core fixtures in ways that break the API test suite.
- Test/demo accounts and any fixture additions go through `src/lib/db/seeds/seed-e2e-tests.ts` (idempotent).
- Standard repo rules apply: tenant-scoped endpoints if any are added (none expected), migrations via db:generate (none expected), tsc zero errors, PR-based delivery with CI green.

## Background

Shipped 2026-07-06 (see `2026-07-06-coach-lifecycle-and-delivery-ops.md`): the ops catalog with ~63 activities and 12 roles generates role manuals via `catalog:render` with a CI up-to-date check; the coach manual and team-captain manual are hand-authored (generator skips `manual_target: hand_authored`). Coach lifecycle (hire → onboard → sequenced plans → assessment) is live. Playwright e2e infrastructure exists with hydration-beacon conventions and seeded test accounts per role. Nothing today produces slides, videos, or any visual training material; onboarding staff currently means reading manuals.

**Out of program scope:** voiced/narrated video rendering (Phase 3 delivers narration *scripts*; TTS muxing is an optional stretch requiring an external API key the user must supply); LMS/quiz features; translating content; parent/player-facing tutorials (worker roles only for v1).

## Phase 1 — Per-role training deck generator

**Why first:** highest value per effort — the content source (catalog + manuals) already exists and is CI-guarded; this adds a presentation layer that inherits that freshness guarantee.

**Scope (in):**
- `src/lib/ops-catalog/views/training-deck.ts`: `renderTrainingDeck(catalog, roleId, opts)` + `generateAllTrainingDecks(catalog)` for worker roles. Slide sections per role: title/role summary; "your day" phase-by-phase (from the role's accountable/responsible activities, reusing the manual view's matching logic); per-activity slides (trigger, steps, tracking, escalation — condensed to bullets); checklist slides (from artifact templates the role touches); safety/escalation summary; "your tools" (role-relevant portal pages — coach: `/coach` surfaces incl. onboarding checklist, practices/sequences, assessments; referee: check-in + score entry; venue manager: venue command center); where-to-get-help closing slide.
- Hand-authored composition: an optional `docs/operations/artifacts/training/role.<id>.intro.md` is inlined as opening slides when present (same skip-protection philosophy as manuals — generator reads it, never writes it).
- Deck shell: single HTML file, inline CSS (project's editorial cream design tokens per `docs/design-system.md`), arrow-key/click slide nav via a small inline script, `@media print` one-slide-per-page.
- Screenshot slots: slides reference screenshots by stable filename (`training/screenshots/<role>/<slug>.png`) and degrade gracefully (hidden block) when absent — Phase 2 fills them. Embed as relative paths, with a `--embed` mode that inlines available images as data URIs for a fully portable deck.
- Wire-up: `scripts/ops-catalog/index.ts` renders decks alongside manuals; `npm run catalog:render` covers both; unit tests in `tests/unit/ops-catalog/views/training-deck.test.ts` (fixture catalog: correct role filtering incl. hand_authored intro composition, stable output, print CSS present); CI up-to-date check inherits automatically.

**Scope (out):** per-organization branding variants; deck content beyond what catalog/manuals contain (no invented procedures).

**Acceptance:** `npm run catalog:render` emits decks for all worker roles; coach/referee/venue-manager decks open from disk, navigate, and print cleanly; unit tests green; re-render is a no-op when the catalog is unchanged; ops-catalog CI check passes.

## Phase 2 — Walkthrough video & screenshot pipeline

**Scope (in):**
- `training/playwright.config.ts`: separate project, `video: { mode: 'on', size: 1280x720 }`, screenshots on, base URL from `TRAINING_BASE_URL` (default `http://localhost:4321`), workers=1, NOT discovered by the main config.
- `training/walkthroughs/*.walkthrough.ts` — scripted tours with a tiny shared helper lib (`training/lib/tour.ts`): `step(page, caption, fn)` records step boundaries + timestamped captions to a JSON sidecar, pauses briefly for watchability, and saves a named screenshot per step into `training/screenshots/<role>/…` (feeding Phase 1's slots).
- v1 walkthroughs (six core workflows): coach-core (roster → attendance → assess a player → notes), coach-practices (view assigned sequence drafts → adapt → complete + reflection), admin-hire-compliance (application list → mark hired → credentials grid → confirm onboarding), admin-sequencing (author sequence → attach to season), referee-gameday (check-in → score entry, to the extent the referee surface supports it — scout first, scope to what exists), venue-manager (venue command center tour).
- Output: `training/output/<workflow>/video.webm` + `captions.json` + per-step screenshots; `npm run training:videos` (all) and `npm run training:videos -- <name>` (one). Output dir gitignored.
- Fixture hygiene: any workflow needing writes uses training-specific fixtures added idempotently to `seed-e2e-tests.ts`; document in each walkthrough header what it writes.
- Docs: `training/README.md` — regen instructions, prerequisites (dev server up via with-bws), where output lands, how decks consume screenshots.

**Scope (out):** CI execution of walkthroughs (manual/on-demand only in v1); hosting/distribution of videos (user decides where they live).

**Acceptance:** one command regenerates all six videos + screenshots against a running dev server; re-running `catalog:render --embed` after a video run produces decks with real screenshots; main `npm test` and CI are unaffected.

## Phase 3 — Narration scripts (+ optional TTS)

**Scope (in):** `training/narration/<workflow>.md` generated from each walkthrough's captions JSON (`npm run training:narration`) — numbered, timestamped voiceover script per video, written for a human reader or TTS input; a deck appendix slide linking each workflow's video + script.

**Scope (out / stretch, only if the user supplies a TTS key):** `training/scripts/tts-mux.ts` — captions → audio via a TTS API → ffmpeg mux over the webm. Gated behind `TRAINING_TTS_API_KEY`; absent key = graceful skip. Do not build until the user opts in.

**Acceptance:** every video has a narration script whose steps match its captions; regenerating after a walkthrough change updates the script.

## Sequencing & delivery

| Phase | Ships | Depends on |
|---|---|---|
| 1. Deck generator | catalog view + tests + rendered decks | — |
| 2. Video pipeline | walkthrough project + 6 workflows + screenshots | Phase 1 for screenshot slots (soft — slots degrade gracefully) |
| 3. Narration | scripts generator (+ optional TTS) | Phase 2 captions |

Update flow after any future feature change: adjust catalog/manuals as usual (decks auto-regen under CI), re-run `npm run training:videos` + `training:narration`, review, commit scripts/screenshots. Each phase: task-level plan (writing-plans) → Sonnet implementation in a worktree → verification sweep → PR with CI green.
